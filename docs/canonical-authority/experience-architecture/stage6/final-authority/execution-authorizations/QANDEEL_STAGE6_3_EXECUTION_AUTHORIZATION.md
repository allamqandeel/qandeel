# 1. EXECUTION-GATE EG-63-01
## Every lifecycle expression must be temporally entitled

OPEN-15 may resolve a structural Experience vocabulary for lifecycle state.

But every rendered lifecycle cue must satisfy:

```text
Cue(state, TC) only if the state/history fact expressed by that cue is legitimate in K(TC)
```

This is especially important for **Reopened**.

A cue that communicates:

> “this Thread was dormant and later reopened”

is not merely a style. It is a historical claim.

Therefore:

- before the dormancy/reopen history is legitimate, no “reopened scar”, ring, marker, notch, trail, badge, memory trace or equivalent may appear;
- if the v1 solution includes a persistent historical trace, that trace must itself have a `KF`/validity entitlement;
- if the v1 solution communicates only the current lifecycle state, it must not accidentally imply unavailable transition history;
- Dormant must remain present at the established Home locus;
- Reopened must remain the same canonical Thread identity and Home locus.

Do not use a future-known lifecycle history as a visual explanation of an earlier projection.

# 2. EXECUTION-GATE EG-63-02
## Sparse-history orientation must be projection-state information, never missing-content information

OPEN-16 may create a truthful orientation cue.

The cue's subject must be equivalent to:

> **“You are viewing an earlier legitimate projection of the same Map.”**

It MUST NOT communicate or imply:

- how many objects are absent;
- that named objects will appear later;
- where absent objects would be;
- that the current field is “incomplete” relative to Live;
- a percentage/progress of Map completion;
- a future density comparison;
- a future spatial direction.

The cue must not derive its prominence, wording, size, placement or behavior from the quantity or identities of unavailable future material.

Required invariant:

```text
SparseCue(K(TC))
must remain equivalent for any two worlds
whose user-entitled historical projection/orientation facts are equivalent,
even if their future-unavailable object counts differ radically.
```

At minimum test:

```text
1 future-unavailable object
vs
100 future-unavailable objects
```

The sparse cue itself must not reveal the difference.

# 3. EXECUTION-GATE EG-63-03
## Perceptual stability is stricter than anchor-coordinate stability

For OPEN-17, fixed Home coordinates are necessary but not sufficient.

A historical projection can technically preserve coordinates while still appearing to “re-layout” if surrounding expression changes too aggressively.

Therefore the final bounds must distinguish:

## A. Canonical geometry — immutable under projection
Examples:
- Established Thread Home locus
- topology/identity commitments already frozen upstream
- camera unless an explicit act moves it

## B. Semantic expression — may change only when truth legitimately changes
Examples potentially include:
- presence/absence of legitimately entitled relations;
- then-valid contextual appearances;
- legitimate lifecycle state expression;
- Session/Reading disclosure at entitled depth.

## C. Ambient/decorative expression — may vary only inside a conservative stability envelope
It MUST NOT:
- move anchors perceptually;
- imply new relation/importance/ownership/confidence;
- compensate for sparse history;
- create a future-shaped void;
- make a Thread appear to migrate.

Stage 6.3 must produce **invariant bounds**, not merely “keep it subtle”.

If a variation channel cannot be bounded without subjective styling judgement, either:
- exclude it from the v1 semantic contract; or
- preserve it as a 6.5/visual-system parameter only if the OPEN-17 reversible-seam conditions remain provable.

Do not invent numeric pixel thresholds merely to appear precise unless research supports a meaningful implementation-independent threshold.

# 5. EXECUTION-GATE EG-63-05
## `IF_ref` continuity chrome must never become a hidden second render of unavailable truth

OPEN-18 may need inspection/return chrome to explain divergence.

But continuity chrome must not recreate the unavailable object/version/context in miniature.

It may communicate only knowledge legitimately available at `TC`.

Required distinctions:

## Case A — identity unknown at TC

Allowed:
- generic inspection-continuity statement;
- generic return action where already authorized.

Forbidden:
- future identity name;
- future version label;
- future context;
- future locus;
- future thumbnail/silhouette.

## Case B — identity known, requested future version unknown

Allowed:
- canonical identity only to the extent already known at `TC`;
- generic statement that the requested inspection cannot be rendered in this historical view.

Forbidden:
- future version name/details;
- future-state thumbnail;
- silent rebind.

## Case C — identity known, requested context unavailable

Allowed:
- canonical identity where known;
- truthful unavailable-in-this-context state.

Forbidden:
- substituting another context;
- naming future context if unknown;
- moving camera to an alternate locus to keep continuity.

## Case D — requested version known but noncurrent

Allowed:
- exact known requested version may remain named as `IF_ref`;
- historically then-current render remains default Map truth;
- deliberate Source/Provenance retrieval may expose known historical lineage.

Must be unmistakable that:
- requested reference is retained;
- current historical Map render is different by design;
- no overwrite/rebind occurred.

## Case E — depth withheld

Must use ordinary Semantic Zoom disclosure logic.

Do NOT use historical-unavailability language.

The candidate must prove users can distinguish D from E.
