## 3. Independent render validation

I-08B2.4 recorded as risk R-1 that its host had no SVG engine, so its boards came from a
numerical model of the layers its files declared, and an independent renderer should
confirm them. **That gap is now closed.**

**Renderer: Chrome 153.0.8010.48 (Blink / Skia), headless**, driven at
`--force-device-scale-factor=1 --force-color-profile=srgb`, rasterising each SVG at the
exact target pixel size rather than resampling from another size. Microsoft Edge
153.0.4234.48 is also present on the host as a second Chromium-family engine.

Every PNG in this package, every measurement in §9, and every tile on every review board is
a real render from that engine. Nothing in this package is drawn by a numerical model.

What this confirmed about the earlier work:

- The approved luminous Q renders correctly through a real engine: the `mix-blend-mode:
  screen` halo, the `feGaussianBlur` + `feComponentTransfer` stroke bloom, the structural
  core tint and the ring/tail non-zero winding overlap all behave as I-08B2.3 specified.
- I-08B2.4's small-size finding reproduces exactly: at 32 px the structural light-point
  core covers **0 whole pixels** (0.36 px²), and the light point survives on the luminous
  presentation rather than on the core.
- I-08B2.4's numerical model was **conservative** about the light point. It predicted a
  peak luma of 205.6 for Variant B at 32 px; the real engine renders 232.4 against a field
  of ~11. The direction of the earlier finding holds; its magnitude was understated.

## 4. App icon

### 4.1 Canonical source artwork

`/app-icon/APP_ICON_B_DARK_LUMINOUS.svg` is the frozen I-08B2.4 Variant B file, carried
across byte for byte. It is conceptually square, full bleed, with no mask shape baked in.

Its internal header comment predates the I-08B2.4 freeze and still reads "NOT approved, NOT
frozen, NOT canonical". It was **not** edited, because editing it would break the hash that
ties this package to the frozen artefact. This is recorded as limitation L-1.

### 4.2 iOS

iOS displays the whole square, corner-masked only. The approved square composition is
therefore what iOS shows, and it is used **unchanged** — no iOS-specific framing was needed
or applied.

- Full classic asset catalogue: 13 distinct pixel sizes (20, 29, 40, 58, 60, 76, 80, 87,
  120, 152, 167, 180, 1024) plus `Contents.json`, covering iPhone, iPad and the 1024
  marketing icon.
- **Written without an alpha channel** (PNG colour type 2). An app icon carrying
  transparency is rejected at submission.
- No rounded-corner shape is baked into any export. The corner treatment is the platform's.
- Tail clipping: none at any size. Edge ink: none at any size (measured, §9).

### 4.3 Android

`mix-blend-mode` and SVG filters **do not exist in Android's VectorDrawable format**, so
the luminous layer cannot be translated to vector. The export method is therefore split by
what each layer actually needs:

| layer | format | why |
|---|---|---|
| background | colour resource `#0A0B0D` | Variant B's ground is a flat colour, so it needs no raster at all and cannot band |
| foreground | PNG, 5 densities (108, 162, 216, 324, 432 px) | carries the screen-blended halo and the Gaussian bloom, which vector cannot express |
| monochrome | VectorDrawable | carries no filter and no blend, so the approved path data goes across **verbatim** |
| legacy launcher | PNG, 5 densities (48–192 px) | pre-API-26 fallback, square and round |

**Why the foreground is a full-bleed opaque raster rather than a transparent logo layer.**
A layer split would change the approved appearance. The halo is a *screen* blend, and
screening over the mark's own ink gives a near-white core while screening over the ground
gives amber — so pre-compositing the halo against the ground alone would turn the
white-hot light point amber where the two overlap. Baking the whole Variant B composite
keeps the approved result exactly. Because the adaptive background is the identical flat
colour, an opaque foreground costs nothing: parallax reveals only more of the same field.

The monochrome layer doubles as the Android 13+ themed icon and as required derivative 6.

## 5. Platform framing, declared numerically

Android authors adaptive icons on a **108 dp** canvas, reserves the outer **18 dp** per side
for masking and effects (leaving a **72 dp** visible viewport), requires key content to stay
inside the **66 dp** safe zone that no OEM mask clips, and specifies a logo of **48–66 dp**.
These figures are from Android's own documentation, checked against it for this task.

| | iOS / canonical square | Android adaptive |
|---|---|---|
| logo size on the 108 dp canvas | 66 dp (the maximum) | 48 dp (the minimum) |
| placement matrix | `0.312622 0 0 0.312622 244.616708 340.621763` | `0.227361 0 0 0.227361 317.539813 387.361532` |
| mark enclosing circle | 625.8 px of 1024 | 455.1 px of 1024 |
| ink box | 534.45 × 386.36 px = 56.37 × 40.75 dp | 388.69 × 280.99 px = 40.99 × 29.64 dp |
| margins L/R, T/B | 244.77, 318.82 px | 317.65, 371.51 px |
| light point centre | (452.14, 623.79) | (468.47, 593.31) |
| light-point core radius | 10.80 px | 7.85 px |
| halo radius | 101.47 px | 73.79 px |
| bloom sigma | 3.46 px | 2.52 px |
| halo outer edge from canvas centre | 228.28 px | 166.02 px |
| safe circle radius (66/108) | 312.89 px | 312.89 px |
| **mark as a fraction of what the user sees** | **61.11% of icon width** | **66.67% of the 72 dp viewport** |

**The framing judgement.** Android crops to its 72 dp viewport; iOS does not crop at all. If
the approved square were shipped to Android unchanged, the mark would occupy **91.67%** of
the Android viewport against **61.11%** of the iOS icon — the same artwork reading half
again as large on one platform. The brief permits platform-specific framing exactly to
prevent that. Exact perceptual parity would need a **44.0 dp** logo, which is below
Android's documented 48 dp floor, so **48 dp** was used: the closest permitted value,
leaving a 9.1% linear difference between the platforms instead of 50%.

Only framing differs between the two platforms. Geometry, colour, bloom and halo are
identical, and both matrices are uniform, unmirrored and unskewed (verified, §10).

Note that the Android mark at 48 dp sits well inside the 66 dp safe zone, and its halo's
outer edge reaches 166.02 px against a 312.89 px safe radius — comfortably inside. On the
iOS/canonical framing the halo reaches 228.28 px, also inside.

## 7. Monochrome rule

**The light point needed no substitute, and none was introduced.**

Reading the approved geometry: `q-light-core` is a disc of radius 34.54 centred at
(663.82, 905.8), which is exactly the midpoint of the tail's inner terminal edge. The tail
begins at x = 663.82 and is about 18.6 units deep there, so the core disc — nearly four
times that radius — stands clear of the tail on every side, and it sits inside the ring's
counter, where no other ink reaches. It is a structural bulb, not a glow artefact.

Consequence: under a single flat ink the light point remains a visible round terminal on
its own geometry. Measured structural presence (departure from the field at the core,
1.000 = fully inked) is **1.000 at 256 and 128 px, 0.994 at 64 px, 0.74 at 32 px** for the
monochrome Q — the same values as the base master, because it is the same geometry.

Both monochrome files are authored as `currentColor`, so they take any single ink; the
declared black is only a fallback. `FINAL_WORDMARK_VARIANTS_BOARD.png` and
`FINAL_LIGHT_DARK_MONO_BOARD.png` show the same file tinted two opposite ways.

Geometry, tail, spacing and proportions are untouched. The wordmark monochrome carries both
light points, including `centre-light-core` at (7541.79, 497.87).

## 8. Light-background rule

Only the ink value changes. The light-background treatment uses **`#0A0B0D`** — the
approved dark neutral ground colour of the canonical app icon — so no new colour is
introduced anywhere in this package.

No glow is carried onto a light field, because a luminous treatment cannot read there. An
amber light point was considered and rejected on measurement: amber against a light field
has poor contrast and the light point would weaken, whereas the flat dark core measures
16.75:1 against `#F4ECDB`. Keeping the ink flat is the technically necessary choice, not a
stylistic one.

The light-background files carry no background of their own, so they composite onto any
light surface.

Structurally, the light-background treatment and the monochrome treatment are the same
artwork at different ink values. That is stated plainly rather than differentiated
artificially: inventing a difference would be inventing a visual style.

## 9. Small-size validation

Measured on real renders at 256 / 128 / 64 / 32 px as required, and additionally at 40, 29
and 20 px for the icons, because those are the smallest sizes iOS actually ships and they
sit below the required floor. Full data: `/review/small-size-validation.json`.

### 9.1 Results

| check | result |
|---|---|
| **tail survival** | 1.000 at every required size for the square icon, the Q luminous master, the monochrome Q and the light-background Q. The Android masked view reads 0.984 at 64 and 32 px — one tail column of 64 falling below the ink threshold, not a break. Weakest column across all targets 0.204–0.74. |
| **tail tip** | present at every size and every target; weakest reading 0.498 (Q base at 32 px), 0.552 (square icon at 20 px). Never lost. |
| **ring counter** | 0.979–1.000 everywhere. The Q never fills in. |
| **light-point continuity** | structural presence 0.576–1.000 across every target and size. Never absent. |
| **halo behaviour** | chroma above the mark's own ink measured 50–96 on luminous targets at every size, and 0–1 on the base, monochrome and light-background treatments — the halo is present exactly where it should be and absent where it should be. |
| **perceived centring** | ink bounding-box offset from canvas centre ≤ 1.0 px at every size on every target. |
| **clipping** | zero edge ink on every icon at every size. The Q masters meet all four borders, which is expected: their viewBox is the ink's own bounding box. |
| **contrast** | ink against field 16.75:1 (icon), 17.44:1 (Q luminous), 21.0:1 (monochrome on white), 16.75:1 (light-background). Measured stroke contrast falls to 10.02:1 at 20 px through antialiasing, still far above any legibility threshold. |

### 9.2 The light point below 64 px

The structural core stops covering whole pixels at 64 px and below: 22.89 px² / 23 whole
pixels at 256, 5.72 / 4 at 128, 1.43 / 0 at 64, 0.36 / 0 at 32, 0.14 / 0 at 20. This
reproduces I-08B2.3's finding exactly. **Geometry was not changed.** The luminous
presentation carries the perceptual continuity below that threshold, which is what the
approved direction was for; the light point was not deleted, enlarged or moved.

### 9.3 The ring opening below ~64 px — finding, and why nothing was changed

The Q's ring is an annulus cut once. The opening measures 115.76 units in the approved
geometry, which at the canonical framing is 2.26 px at a 64 px icon and 1.13 px at 32 px.
Measured openness (1.000 = fully open): **1.000 at 256 and 128, 0.994 at 64, 0.664 at 40,
0.581 at 32, 0.433 at 20.** Below about 64 px the opening softens.

The question that decides what to do is whether the stroke bloom closes it or resolution
does, because the brief permits a tiny-size adjustment to rendering, halo or export
treatment but not to geometry. That was measured directly, rendering the canonical icon
with the approved bloom, a reduced bloom and no bloom at all:

| size | gap width | no bloom | slope 0.15 | slope 0.35 (approved) |
|---|---|---|---|---|
| 64 px | 2.26 px | 0.994 | 0.994 | 0.994 |
| 48 px | 1.70 px | 0.786 | 0.769 | 0.736 |
| 40 px | 1.41 px | 0.728 | 0.701 | 0.664 |
| 32 px | 1.13 px | 0.631 | 0.610 | 0.581 |
| 20 px | 0.71 px | 0.508 | 0.475 | 0.433 |

**Removing the bloom entirely recovers only 0.05–0.08 of openness.** Resolution dominates.
No export treatment can reopen a sub-pixel gap, so changing the approved luminous treatment
would alter the frozen direction for no meaningful gain. **Nothing was changed.** This is
recorded as a characteristic of the mark at very small sizes, L-2.

### 9.4 Two measurement corrections

Both were fixed in the tools rather than reported as findings:

- A single nearest-pixel probe of the ring opening is a function of sub-pixel phase, not of
  the artwork: it read 0.889 at 29 px and 0.405 at 32 px on identical geometry. The opening
  is now sampled bilinearly right across the channel between the two radial edges. A
  residual non-monotonicity remains at 29 vs 32 px and is irreducible — the feature is
  about one pixel wide there.
- Light-point and halo metrics originally assumed light ink on a dark field and reported
  nonsense for the monochrome and light-background treatments (peak luma 255 from the white
  field, zero energy). They are now direction-agnostic, and halo chroma is measured relative
  to the chroma the mark's own ink and field already carry — without that subtraction a warm
  ink on a warm field reports a halo that is not there.

## 10. Geometry verification

`/review/GEOMETRY_VERIFICATION.json` — **39 checks, 39 passed.**

Text equality alone would not catch a distorting placement transform, and a render check
alone would not catch silent re-rounding of path data, so both were done:

1. All four masters hash to their frozen values; all packaged copies are byte-identical.
2. The canonical app icon is the frozen I-08B2.4 Variant B, byte for byte.
3. Every shipped SVG's path data is **byte-identical** to the master's — 3 paths for each Q
   file, 10 for each wordmark file — with exactly one copy of each per file.
4. Both placement matrices are uniform, unmirrored, unskewed and equal to the framing this
   task declares.
5. The geometry each file actually carries renders **pixel-identically** to the master's
   through the real engine, in a shared harness frame: **0 differing pixels** at 1400×1012
   for every Q file and 1400×174 for every wordmark file.
6. The Android VectorDrawable's `pathData` is byte-identical to the master's three paths,
   its group transform is uniform and as declared (0.02397948), and all three paths declare
   `nonZero` fill — which is what keeps the ring/tail overlap solid.
7. Purity: no `data:` URI, no raster, no external reference in any shipped SVG.

**No geometry was changed. No redesign occurred.**

## 11. Technical limitations — all non-blocking

- **L-1.** The canonical app-icon SVG carries an internal header comment written before the
  I-08B2.4 freeze, still reading "NOT approved, NOT frozen, NOT canonical". It was
  deliberately not edited, so the file still hashes to the frozen artefact. If Product wants
  the comment corrected, that is a one-line change that will change the file's hash, and it
  should be done as an explicit decision rather than silently here.
- **L-2.** The ring opening falls below one pixel at icon sizes under about 40 px and reads
  as a softening rather than a clean break. Measured, quantified in §9.3, and not
  attributable to the luminous treatment. No geometry or export change was made.
- **L-3.** Android's foreground layer is a raster, not a VectorDrawable, because
  `mix-blend-mode` and SVG filters have no VectorDrawable equivalent. The monochrome layer
  *is* a VectorDrawable. This is the export method the brief anticipated, documented in §4.3.
- **L-4.** The approved masters are framed tight to their own ink — the wordmark's ink
  bounding box reaches the viewBox edge to within 0.5 units on the left and exactly 0.000 on
  the right. Nothing is clipped, but the masters carry **no clear space**, so any production
  use must add its own. Verified rather than assumed: ink overflow is 0.000 right, and
  negative (clearance) on the other three sides.
- **L-5.** iOS 18 dark and tinted icon variants are not included. They were out of scope for
  this task and would need their own Product direction, since a tinted variant is a
  single-channel treatment of the mark rather than a recolour of Variant B.
- **L-6.** Legacy round Android launcher PNGs carry a baked circular mask. That is a
  platform delivery requirement for pre-API-26 round launchers, not a shape baked into the
  design; the adaptive path and every other asset stay conceptually square.
- **L-7.** Validation was performed on one rendering engine family (Chromium 153, Blink /
  Skia). It is a real, independent engine and it closes I-08B2.4's R-1, but it is not
  coverage of Core Graphics on iOS or Skia-via-Android's own drawable pipeline. Those are
  device checks, not host checks.
