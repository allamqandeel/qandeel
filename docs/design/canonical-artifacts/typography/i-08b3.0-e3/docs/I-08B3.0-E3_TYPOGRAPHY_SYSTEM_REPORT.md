# I-08B3.0-E3 — Typography System Proof & Stress Validation

**Status: READY FOR DESIGN DIRECTOR TYPOGRAPHY FREEZE REVIEW.**
Not approved, not frozen, not canonical. E2 is not frozen and I-08B3.0 is not closed by this document.
The typeface is not under test: **Estedad v8.5 is accepted** and this package tests only the *system*
proposed around it. No stop condition was triggered.

This proof was built to look for failure. Where the proposed contract holds, the report says so and says
what was tried; where it is weak, the weakness is reproduced on a board and measured. Two claims that the
first draft of this package made were withdrawn during execution because measurement contradicted them —
both are documented in §12 and §15 rather than quietly removed.

## 2. References inspected

Primary sources only. No inspiration blogs, and nothing quoted from a font's marketing page.

**A. Apple.** *Human Interface Guidelines — Typography*, read in full including the Specifications tables.
Recorded: iOS default 17 pt / minimum 11 pt; "avoid light font weights … prefer Regular, Medium, Semibold,
or Bold"; the complete iOS Dynamic Type ladder from xSmall through AX5; and, for §7, the explicit statement
of intent — *"when people increase text size … they don't always want to increase the size of every word on
the screen."* Also *"Keep text truncation to a minimum as font size increases"*, *"consider using a stacked
layout where text appears above secondary items"*, *"Maintain a consistent information hierarchy regardless
of the current font size"*, and — directly relevant, because Estedad is a custom face — *"Implement
accessibility features for custom fonts … If you use a custom font, make sure it implements the same
behaviors."* *HIG — Right to left* supplied the testable claim that Arabic beside uppercase Latin "can appear
too small" and should be raised by about 2 points; §10 measures that claim against this typeface and does
not adopt it.

**B. Android.** AOSP source, read at source rather than summarised:
`frameworks/base/core/java/android/content/res/FontScaleConverterFactory.java` (the eight nonlinear
lookup tables for scale keys 1.05 → 2.00, and `forScale`'s linear interpolation between the two nearest
tables) and `FontScaleConverterImpl.java` (`convertSpToDp` / `lookupAndInterpolate`: interpolate inside the
table, interpolate from 0 below the first entry, apply the final entry's ratio above the last). These tables
are transcribed verbatim into `tools/scale.mjs` with a self-check that fails the build if they drift.

**C. W3C.** *Arabic & Persian Layout Requirements* (`alreq`): §7.2 — *"Lines of Arabic script text are
normally right aligned within the page"*, and the warning that "excessive use of kashida … results in uneven
colour"; §7.1 on wrapping between words; §7.3 on stretching being non-equidistant, which is the technical
reason the contract's zero-letter-spacing rule is not merely stylistic.

**D. Estedad.** The binary itself (`name`, `OS/2`, `hhea`, `fvar`, `GSUB`/`GPOS` tables), the upstream
release notes for v8.5 and v8.4, and the open issue tracker. Four open issues were read; two are reproduced
and measured in this package — **#39 "Mark to base bug"** (§12) and **#44 "English letter i not displaying"**
(§12). v8.5 is the current release; its notes record an interpolation fix in `osmall` and the resolution of
an hhea/OS-2 vertical-metric mismatch. The mark work the issue tracker discusses landed in **v8.4**
("Adjusted vertical positioning of Arabic mark diacritics for standalone usage without base glyphs").

## 6. Exact line-heights, as rendered

Line-height was applied as a **unitless multiple of the size** (`line-height: ratio`), computed from the
declared pair, so the ratio is preserved under scaling. The alternative model — leading as an absolute
value — is rendered too, on the failure board, because the contract does not say which one it means. See
§7 and §13 (C-1); this is the single most consequential ambiguity found.

At 100 % the rendered values are exactly the declared pairs. No per-role tuning, no optical adjustment, and
**no letter-spacing on any Arabic element anywhere in this package.**

## 7. Scaling method

**Android 14+ nonlinear font scaling, implemented from the AOSP tables, not simulated.** The brief forbids
multiplying every layout dimension, and the platform does not do that either. Only *type sizes* pass through
the curve; dp paddings, gutters, radii and minimum touch heights are left alone, exactly as a real device
leaves them.

160 % is not a table key, so it is produced the way `forScale` produces it: linear interpolation between the
1.50 and 1.80 tables at t = 1/3.

**What the curve does to this contract:**

| Role | Base | 130 % | 160 % | 200 % | Growth at 200 % |
|---|---|---|---|---|---|
| MEANINGFUL STATEMENT | 32 | 32 | 33.6 | 39.8 | **×1.243** |
| SCREEN TITLE | 26 | 27.6 | 30.3 | 36.7 | ×1.410 |
| SECTION TITLE | 20 | 23.6 | 27.6 | 34 | ×1.700 |
| PRIMARY BODY | 17 | 20.9 | 24.6 | 29 | ×1.706 |
| SUPPORTING BODY | 15 | 19.5 | 23.4 | 27 | ×1.800 |
| ACTION / LABEL | 14 | 18.8 | 22.8 | 26 | ×1.857 |
| METADATA | 12 | 15.6 | 19.2 | 24 | **×2.000** |
| NUMERIC READING | 20 | 23.6 | 27.6 | 34 | ×1.700 |

**The curve is not uniform, and that is the headline finding of the accessibility work.** At 200 % METADATA
doubles while MEANINGFUL STATEMENT grows by under a quarter. At **130 % the statement does not move at all**
(×1.000) while metadata grows 30 %. The ratio between the largest and smallest role therefore falls from
**2.67× at 100 % to 1.66× at 200 %** — the hierarchy compresses by 38 % for precisely the people who most
need large text.

This is deliberate platform behaviour, not a defect, and **iOS does the same thing in the same direction**:
Body 17→53 pt (×3.1) against Large Title 34→60 pt (×1.8) across the full Dynamic Type range. Apple states
the intent openly (§2A). The consequence for this contract is simply that **it cannot assume its proportions
survive scaling**, and any hierarchy that depends on "32 reads as much bigger than 12" needs a second signal.

**Page growth** (one body paragraph, 360 px phone, measured in the engine): 100 % → 7 lines / 210 px;
130 % → 9 / 332 px; 160 % → 10 / 434 px; 200 % → 12 / 614 px (**×2.93**). Content reflows and the page gets
longer. **Nothing was clipped, truncated, hidden or overlapped at any scale on any device tested.**

## 8. Reading-measure findings

The same 548-word passage at PRIMARY BODY 17/30 across five column widths, all other conditions identical.

| Measure | Lines | Chars / line | **Words / line** | Eye travel | Height |
|---|---|---|---|---|---|
| 328 px — narrow phone, full bleed | 70 | 43.6 | **7.8** | 19.3 em | 2100 px |
| 480 px — unbounded tablet third | 47 | 65.0 | **11.7** | 28.2 em | 1410 px |
| 560 px — candidate A | 40 | 76.4 | **13.7** | 32.9 em | 1200 px |
| 640 px — candidate B | 35 | 87.3 | **15.7** | 37.6 em | 1050 px |
| 704 px — 768 px tablet, unbounded | 32 | 95.3 | **17.1** | 41.4 em | 960 px |

Arabic words in this passage average 5.6 characters, so the familiar Latin 45–75 character guidance does not
transfer; **words per line is the honest quantity for Arabic**, and the return sweep is what tires the eye.

- At **328 px** the line carries 7.8 words over 70 lines. The eye returns constantly. This is acceptable on
  a phone because there is no alternative, but it is the *least* comfortable condition in the set, not the
  best — worth saying because a phone-first product can mistake familiarity for comfort.
- At **704 px** — a 768 px tablet with nothing holding the text back — the line carries 17.1 words over
  41 ems of travel. Losing your place on the return becomes likely and the paragraph loses its rhythm. This
  is exactly the condition the contract's reading-column principle exists to prevent, and the board shows it
  beside a bounded column on the same 768 px screen.
- Against a 10–15 words-per-line target, **480 px and 560 px are comfortable and 640 px is already long**.
  The upper boundary lies between 560 and 640.

**Finding: a reading column in the region of 520–600 px is where this passage holds its shape best.** This
is a range offered for judgement and **not a frozen token** — the right value also depends on gutters, on
whether a second column of interface sits beside the text, and on which tablet sizes the product supports.

One thing worth flagging beyond the analysis screen: the **conversation** view on the same 768 px tablet runs
to 17 words per line for the same reason (`CONVERSATION_100`, tablet column). Whatever measure is chosen, the
question is not confined to PROOF B.

## 9. Mixed-script findings

**Relative sizes, measured from shaped text:**

| Quantity | Measured (em) |
|---|---|
| Arabic ink height (`الثقة`) | 0.710 |
| Latin cap height | 0.660 |
| Latin lowercase ascender | 0.7074 |
| Latin x-height | 0.500 |
| **Arabic ÷ Latin cap** | **1.0758** |

**The contract's "no blanket ±2 px correction" rule is correct for this typeface, and the measurement is the
reason.** Apple's RTL guidance warns that Arabic beside uppercase Latin can appear too small and suggests
raising it ~2 pt — but that advice is about the system fonts. In Estedad the Arabic already stands **7.6 %
taller** than its own Latin capitals, and the Latin lowercase ascender (0.7074 em) sits within 3/1000 em of
the Arabic ink height. Applying the +2 pt correction here would over-correct in the wrong direction. Both
scripts share one nominal size and one weight, as the contract states, and the shared-baseline specimen on
`MIXED_SCRIPT` shows the result.

**Bidirectional behaviour** was measured per character: each sentence was laid out, every character's
position read back, and the results sorted by x to recover the order the eye actually sees. Seven hard cases
were tested — a trailing Latin token before an Arabic full stop, an Arabic comma after an identifier, a
parenthesised identifier, two adjacent Latin runs, a hash and digits (`PR #220`), an Arabic-Indic percentage,
and a version token mid-sentence.

**All seven laid out correctly.** Latin runs stay internally left-to-right, brackets mirror, the Arabic-Indic
percentage keeps its sign on the correct side, and the sentence-final stop lands at the left edge as RTL
requires. **Wrapping the Latin runs in explicit isolates (U+2068 / U+2069) changed nothing in any of the
seven cases**, so no directional hack is warranted and none is used anywhere in this package. The contract's
instruction to avoid directional hacks unless a test exposes a genuine need is satisfied: the test was run
and exposed none.

**One genuine observation.** On a 412 px phone, **Memory Runtime breaks across two lines** — "Memory" ends
one line, "Runtime" begins the next. No typographic rule is violated; they are two words separated by an
ordinary space. But a multi-word English term is read as one name, and QANDEEL's vocabulary is full of them
(*Memory Runtime*, *QANDEEL Human Map*). Whether such terms are bound with a non-breaking space is a content
decision, raised here only because this is where it becomes visible.

## 10. Numeral findings

**Measured figure behaviour** (advance per glyph at 100 px):

| Figure set | Default | With `tnum` |
|---|---|---|
| Western 0–9 | 41.0 – 59.7 px (spread **18.7**) | 73.81 px (spread **0**) |
| Arabic-Indic ٠–٩ | 31.7 – 70.5 px (spread **38.8**) | 73.81 px (spread **0**) |

Both systems are proportional by default and **both become tabular on request** — and they reach the *same*
tabular advance (73.81 px), so a column may mix them and still align. Estedad applying `tnum` to Arabic-Indic
digits at all is the uncommon part, and it is what makes an Arabic-Indic metric column possible. This is the
finding that carried over from E1 and it holds under independent measurement here.

The contract's numeral policy is supported by the boards:

- Arabic-Indic for human-facing values (`٧٢٪`, `١٤ سبتمبر`, `٨:٣٤ م`), ASCII source form for technical
  identifiers (`H-04`, `v8.5`, `0.68`, `PR #220`, `SHA-256`). One system per user; nothing is transformed.
- **Tabular figures only where they do functional work.** `METADATA_NUMERICS` shows the same three-row metric
  column across three successive readings, proportional against tabular: the proportional column's right edge
  moves between frames, the tabular one holds still. That is the whole of the functional case.
- **The argument against enabling `tnum` globally is shown rather than asserted.** The same Arabic sentence
  carrying `SHA-256`, `v8.5`, `PR #220` and `0.68` is set twice, once proportional and once with tabular
  forced on. With `tnum` on, every digit is padded to one width and the identifiers visibly loosen inside
  running Arabic. A metadata line read once and never updated gains nothing and loses the natural fit.

**One finding the contract does not currently cover.** METADATA is the one role made almost entirely of
digits and separators, and at 12 px the `·` separator (U+00B7) carries **1.44 px** of ink against the
Arabic-Indic zero's **2.52 px** — two small round marks 1.08 px apart in height, with centres 0.125 em apart.
**This was found by misreading this package's own board:** `٨:٣٤ م ·` was read as a time ending in `٠` until
the string was measured character by character. The bullet (U+2022) is the same ink height as the zero and is
distinguished only by sitting higher; the en dash and the vertical bar are structurally different shapes and
cannot be confused with a digit at any size. Which separator the product uses is a design decision and is not
taken here — the confusability is recorded because it exists only where Arabic-Indic digits and a round
separator share a 12 px line, which is exactly the METADATA role.

## 11. Accessibility findings

Kept separate from aesthetic preference, and not reduced to contrast.

- **Text scaling.** At 100 / 130 / 160 / 200 %, across three device classes, for PROOF A, PROOF B and
  PROOF F: **nothing disappeared, clipped, truncated, overlapped, or required horizontal scrolling.** Content
  reflowed, components grew in height, and the page got longer — all permitted. Page length grew ×2.93 at
  200 %.
- **Touch targets.** Every control cleared 48 dp at every scale, because height is content-driven with a
  48 dp floor rather than fixed. No control in this package has a fixed height that could clip its label.
- **Hierarchy without colour.** `TYPOGRAPHY_SYSTEM_OVERVIEW` sets the whole ladder in a single ink. All eight
  roles remain separable by size, weight, leading and spacing alone. The system is legible in monochrome.
- **Contrast, as one input among several.** On the controlled ground (`#0E1013`): primary ink 15.52:1,
  secondary ink 7.30:1. Both clear 4.5:1 for normal-size text with margin. The board's own chrome grey
  measures 4.14:1 and is used *only* for board furniture, never for content — it appears on the failure board
  purely to mark where the floor is. **Colour is not being decided in this task**; the point is narrower and
  worth recording: METADATA is the smallest text in the system and the most likely to be set in the quietest
  ink, so it has the least contrast headroom to give away.
- **Hierarchy compression under scaling** (§7) is an accessibility finding, not a stylistic one: the people
  who raise text to 200 % are the ones who receive the flattest hierarchy.

## 12. Diacritic findings

Nothing was repaired and no glyph was edited. These are the font's own outlines and its own GPOS.

**Clearance.** A fully vocalised Arabic sentence measures **1.598 em** of ink in Estedad v8.5; the same prose
unvocalised measures **1.404 em**; the font's declared line box is **1.525 em**. So plain Arabic prose — which
is what QANDEEL actually sets — clears every role in the contract comfortably. Full vocalisation is what
changes the answer, and it does so for three roles (§13, C-2/C-3).

**The known issue, reproduced — and the upstream report corrected.** Open issue
`aminabedi68/Estedad #39`, filed against v8.5, states that "U+FE74" after shadda "is mispositioned, it should
be below Shadda, not above it". Both encodings were rendered on four bases (ب، د، م، ه) and measured.

- **U+FE74 is ARABIC KASRATAN ISOLATED FORM — a *spacing* presentation-form glyph, not a combining mark.**
  It does not compose with the base at all; it is placed beside the letter as its own glyph with its own
  advance. It **did not raise the ink ceiling on any of the four bases**.
- **U+064D, the combining kasratan — the codepoint a keyboard and an IME actually produce — is the one
  Estedad v8.5 places ABOVE the shadda**, on all four bases, where it belongs below. Measured ink ceilings:
  ب 0.482 → 0.569 em, د 0.688 → 0.776, م 0.608 → 0.696, ه 0.725 → 0.813 em; in every case the mark adds ink
  *upward* and never downward.

**The defect is real, but the issue names the wrong codepoint.** That matters practically: anyone testing
with U+FE74 will conclude the font is fine, and anyone typing normally will hit the defect.

**Measured severity.** The defect requires the exact sequence shadda + kasratan on the same base. It does not
affect unvocalised prose, and it does not affect the tanween forms QANDEEL's content does use — `حقيقيًا`,
`مرةً` — because those carry no shadda. At 17 px and below the misplaced mark is roughly one pixel and reads
as slightly heavier vocalisation rather than as an error; at 32 px it is plainly visible. It becomes a real
QANDEEL problem only if the product ever sets fully vocalised text: Qur'anic quotation, classical poetry, or
teaching material with full tashkeel. **This is consistent with the accepted position that the v8.5 mark
issue is a recorded QA limitation rather than grounds to replace the font.** The board records it with its
trigger and its blast radius so that the limitation is specific rather than vague.

**Mark stacking** (ink above the baseline, in ems): the tallest combination in the set is
qaf + shadda + dammatan at **1.104 em** — the pattern in `مُهِمٌّ`. A standalone shadda + fatha with no base
sits entirely above the baseline (ink floor −0.34 em), which is the v8.4 adjustment for base-less marks
behaving as intended.

**Issue #44 does not reproduce.** The upstream report that the lowercase Latin `i` fails to display (Office
2013, Windows 10, v8.5) does not occur in this engine: `i` carries a 25.31 px advance at 100 px, its tittle
sits at 0.7074 em, and "Confidence" measures exactly that much wider than "Confdence". Given QANDEEL's mixed
script content is full of the letter (*Confidence*, *Hypothesis*, *Runtime*), this was worth testing rather
than assuming. It appears to be a legacy-shaper problem specific to that application, not a defect in the
font data.

## 13. Failure cases

`TYPOGRAPHY_FAILURE_BOARD.png` carries all of these with the content reproduced at size.

**F1 — three roles have no margin over fully vocalised Arabic, but nothing collides.**
MEANINGFUL STATEMENT (1.563), SECTION TITLE (1.600) and NUMERIC READING (1.500) declare a line shorter than
their own worst-case vocalised ink; ACTION / LABEL clears it by 0.01 px, which is not a margin.

*That arithmetic says the line boxes overlap. It does not say the ink touches, and this package checked
rather than asserted.* Each role's worst case was set as a real multi-line block and the **rendered pixels**
were read column by column: for every pixel column, the longest unbroken vertical run of ink, against what a
single line can occupy. **No role collides.** The tallest mark and the deepest descender of a line are never
in the same column. Measured clearance between adjacent lines, as a fraction of each role's own size:

| Role | Ratio | Clearance | | Role | Ratio | Clearance |
|---|---|---|---|---|---|---|
| NUMERIC READING | 1.500 | **0.450 em** | | SUPPORTING BODY | 1.667 | 0.633 em |
| SECTION TITLE | 1.600 | **0.525 em** | | METADATA | 1.667 | 0.708 em |
| MEANINGFUL STATEMENT | 1.563 | **0.531 em** | | PRIMARY BODY | 1.765 | **0.735 em** |
| SCREEN TITLE | 1.615 | 0.558 em | | ACTION / LABEL | 1.643 | 0.571 em |

The clearance ranks exactly as the ratios predict. **The overlap is a latent condition — there is no room
left for content with heavier vocalisation than this — and not a defect visible today.**

**F2 — the leading model decides whether the system survives 200 %.** *This is the most consequential finding
in the package.* The contract states each role as a "size / leading" pair but does not say whether the leading
is an absolute value or a multiple of the size. If it is absolute and expressed in sp, it goes through the
platform's nonlinear curve *independently of the size* — and because the curve flattens for larger numbers,
the leading grows more slowly than the text it must contain:

| Role | Ratio at 100 % | At 200 %, leading as a multiplier | At 200 %, leading as absolute sp |
|---|---|---|---|
| MEANINGFUL STATEMENT | 1.563 | 39.8 / 62.1 — 1.563 | 39.8 / 55.7 — **1.401** |
| SCREEN TITLE | 1.615 | 36.7 / 59.2 — 1.615 | 36.7 / 48.6 — **1.326** |
| SECTION TITLE | 1.600 | 34 / 54.4 — 1.600 | 34 / 39.8 — **1.170** |
| PRIMARY BODY | 1.765 | 29 / 51.2 — 1.765 | 29 / 38 — **1.310** |
| SUPPORTING BODY | 1.667 | 27 / 45 — 1.667 | 27 / 36.3 — **1.346** |
| ACTION / LABEL | 1.643 | 26 / 42.7 — 1.643 | 26 / 35.5 — **1.365** |
| METADATA | 1.667 | 24 / 40 — 1.667 | 24 / 34 — **1.417** |
| NUMERIC READING | 1.500 | 34 / 51 — 1.500 | 34 / 38 — **1.118** |

**Every role falls below the Arabic floor, and below the font's own 1.525 em line box.** PRIMARY BODY
collapses from 1.765 to 1.310 — worse than Tailwind's `leading-tight`, which `designing-arabic-frontends`
prohibits outright for Arabic. Both renderings are on the board side by side.

**F3 — hierarchy compresses as text scales** (§7). Nothing breaks and nothing clips, but the distance between
the loudest and the quietest role nearly halves.

**F4 — a single Arabic word outgrows a narrow slot at 200 %.** In a 104 px toolbar slot (76 px content box):
at 160 % two labels no longer fit (`الإعدادات`, `الإشعارات`); at 200 % six do not, with `الإشعارات` measuring
104.8 px of text. Arabic does not hyphenate, must not be letter-spaced, and must not be condensed, so there is
no typographic escape — the word is simply wider than the box. The honest answers are a wider slot, a wrapped
collection, or a stacked layout. Shrinking the type is not one of them and the contract already forbids it.

**F5 — 32 may be too large for the phone it has to live on.** Not a legibility failure: 32 is perfectly
legible. But on a 412 px phone the required statement sets to **three lines at 32/50 and two lines at 26/42**,
and at 32 the break falls after `يصبح`, leaving the final word `حقيقيًا.` alone on its own line — which
weakens the moment the role exists to carry. This is a product judgement about how much of the first screen a
single sentence should own, offered as an observation.

**F6 — METADATA at 12 px on the dark ground.** 12/20 holds up at 7.30:1 in secondary ink; counters stay open
and the Arabic-Indic digits stay distinct. Recorded as the role with the least contrast headroom, not as a
failure.

## 15. Evaluation questions

Answered descriptively. **No final Product decision is made in any of these.**

**1. Is 17 / 30 appropriate as QANDEEL's primary Arabic reading centre?**
Yes, and it is the strongest value in the contract. 17 is Apple's iOS default body size exactly; the 1.765
ratio gives the most generous inter-line clearance in the system (0.735 em) and is the only role with real
headroom over fully vocalised Arabic. It reflows cleanly at every scale and on every device tested. Nothing
found argues against it.

**2. Is 15 / 25 meaningfully useful, or redundant?**
Useful, but it is the narrowest gap in the ladder. 15 sits 2 px below PRIMARY BODY and its weight is
identical (400), so on the boards the two are separated by size alone — visible in continuous text, subtle in
isolation. It earns its place where a supporting sentence sits directly beneath a statement (PROOF C) and the
subordination must read without a colour change. It does *not* earn its place as a general second body size.
Under scaling the gap narrows further: at 200 % PRIMARY BODY is 29 and SUPPORTING BODY 27. If the system ever
needs to lose a role, this is the one with the weakest independent case — a judgement, not a defect.

**3. Is 12 / 20 viable for metadata on a dark surface?**
Yes. It sits above Apple's 11 pt iOS floor, measures 7.30:1 in secondary ink, and its counters and
Arabic-Indic digits stay distinct at size on a true pixel grid. Two qualifications, both in §10 and §13: it
has the least contrast headroom in the system, and the `·` separator is confusable with `٠` at this size.
Neither makes 12/20 unviable; both mean it has nothing to give away.

**4. Does 32 / 50 feel appropriate for meaningful statements?**
32 is legible and carries weight without any luminous effect — the role works without glow, which was the
point of testing it bare. Two reservations. First, leading: 1.563 is below the Arabic floor and below its own
worst-case vocalised ink (C-3). Second, and more interesting: on a 412 px phone the required statement takes
**three lines at 32/50 and two at 26/42**, and at 32 the break strands the final word `حقيقيًا.` on a line of
its own. A statement that must be read as one thought is weakened by being broken into three. Whether the
moment is better served by 32 owning most of the first screen or by 26 holding the sentence in two lines is a
product judgement about the role, not a typographic defect — `MEANINGFUL_STATEMENT_COMPARISON` sets it at
26, 32 and 36 so the judgement can be made from evidence.

**5. Are 400 / 500 / 600 sufficient?**
Yes. All three remain distinguishable in a single ink at every role size tested, including 12 px. 400 is the
correct floor for Arabic (`designing-arabic-frontends` and Apple both warn against lighter weights). Nothing
in the stress testing exposed a need for 700+: where hierarchy was under strain the cause was size
compression under scaling (§7), which added weight would not fix, and where labels failed the cause was width
(F4), which added weight would worsen. **No case was found for extending the weight policy.**

**6. Does the type hierarchy remain clear without colour?**
Yes at 100 %. The single-ink panel on `TYPOGRAPHY_SYSTEM_OVERVIEW` separates all eight roles by size, weight,
leading and spacing alone. The qualification is scaling, not colour: at 200 % the statement-to-metadata ratio
falls from 2.67× to 1.66×, so a hierarchy resting on size contrast alone is at its weakest exactly where the
monochrome test matters most. Roles distinguished by *weight* and *spacing* as well as size survive that
compression; roles distinguished only by size do not.

**7. Does Estedad stay comfortable at long reading lengths?**
Yes at an appropriate measure, and the measure is the variable rather than the typeface. Across 548 words the
face holds an even texture with no visible stripes or rivers, and its generous counters carry the 17 px size
well. Comfort is governed by column width: 480–560 px is comfortable, 640 px is already long, and 704 px
(an unbounded 768 px tablet) is where the return sweep starts to fail. See §8.

**8. Does mixed Arabic–English remain balanced?**
Yes, and better than the platform guidance would predict. Arabic stands 7.6 % taller than Estedad's own Latin
capitals and its Latin lowercase ascender is within 3/1000 em of the Arabic ink height, so the two scripts
share one nominal size with no correction — Apple's +2 pt RTL advice would over-correct here. Bidi is correct
in all seven hard cases and isolates change nothing. The one open item is line-breaking of multi-word English
terms (C-7), which is content, not type.

**9. Does the system survive 200 % scaling?**
**Yes, if and only if the leading is a multiplier (C-1).** Under that model: nothing clipped, nothing
truncated, nothing hidden, nothing overlapped, no horizontal scrolling, every touch target still ≥48 dp, and
the page simply grew ×2.93. Under the absolute-sp model it does not survive — every role drops below the
Arabic floor and PRIMARY BODY collapses to 1.310. Two lesser issues remain even under the correct model: the
hierarchy compresses (§7), and narrow label slots overflow (F4) — a layout problem rather than a typographic
one.

**10. Which proposed values, if any, should be revised before freeze?**
Only the leadings, and only three of them: **NUMERIC READING 20/30** (C-2, the tightest in the system and
below the font's own line box), **MEANINGFUL STATEMENT 32/50** (C-3), and optionally **SECTION TITLE 20/32**
(C-4). **Every size in the contract survived testing unchanged** and the weight policy needs no extension.
The most important item before freeze is not a value at all but C-1 — stating what the leading *is*.

## 16. Is a Product decision required before freeze?

**Yes — one, and it is a clarification rather than a redesign.**

- **Required: C-1**, the leading model. The contract cannot be implemented unambiguously without it, and the
  wrong reading fails at 200 % invisibly.
- **Required if NUMERIC READING can wrap: C-2.** If Product can guarantee the role is single-line, no change
  is needed — but the guarantee should be recorded, because 1.500 is below the typeface's own line box.
- **Product judgement, not blocking:** the statement size (F5 — 32 against 26), the reading-column value
  (§8 — a 520–600 px region is proposed, deliberately **not** frozen), the METADATA separator (C-6), the
  minimum label-slot rule (C-5), and non-breaking spaces in multi-word English terms (C-7).
- **No decision needed** on typeface, weights, sizes, numeral policy, alignment, tracking, or the Arabic
  rules — all tested and all held.

## 17. Rendering issues found during execution

Four defects in this package's own harness were found and fixed rather than shipped. Each produced output
that looked entirely finished.

1. **Every measurement was of the wrong font.** Chrome activates a `@font-face` only when something in the
   *parsed* document already uses the family. `document.fonts.ready` resolved and `document.fonts.check()`
   returned `true` while the face had never been fetched, so an element created and measured afterwards
   reported **fallback** metrics. The first full measurement run was internally consistent, entirely
   plausible, and about a substituted face. Caught by the fallback guard (shaped width identical to a
   no-font control). Fixed with a static user of every weight in the initial markup plus an explicit
   `document.fonts.load()` per weight. **Every board now carries a font fingerprint** — the same string
   shaped at 400/500/600 — asserted on every render; three *different* expected widths also prove the
   variable `wght` axis is live.
2. **The font guard shifted the page.** Laid out in normal flow, the three 1700 px probes chain into a
   5100 px run which, in an RTL document, extends *leftward* past the viewport and displaces the body —
   tripping this package's own overflow guard. Fixed by absolutely positioning the probes at one point
   inside a 1 px clipped fixed box.
3. **Board chrome silently lost all its styling.** The OS UI font stack contains `"Segoe UI"` in double
   quotes; inlined into a `style="…"` attribute it closed the attribute early and every declaration after
   `font-family` was dropped, so in-device captions rendered as large light product-looking text instead of
   small grey chrome. Fixed by moving it to a CSS class, with the reason recorded at the definition.

4. **The provenance hash was wrong, for a file of exactly the right length.** `tools/font-facts.mjs` read
   the font, parsed its `name` table, then hashed the buffer. `Buffer.swap16()` — needed to decode
   platform-3 UTF-16BE name strings — **byte-swaps in place**, and a `subarray` is a view onto the same
   memory, so reading the version string silently rewrote those bytes of the file buffer. The digest that
   came out was stable, well-formed, and not the digest of the file on disk. Caught only because it
   disagreed with the value already in the report; PowerShell `Get-FileHash`, `certutil` and a clean Node
   read were then run against each other and all three agreed against it. Fixed by copying before swapping
   **and** by hashing before anything parses. A wrong hash in a provenance document is worse than no hash,
   because it looks like verification.

Also corrected, incidentally: headless Chrome clamps its window to roughly 500 px, so a canvas narrower than
that is reported wider than requested and trips the overflow guard for a reason unrelated to content.

**Two claims this package made and then withdrew**, because measurement contradicted them:

- The failure board initially stated that consecutive lines **collide** for the three sub-1.63 roles. The
  arithmetic supported it; the rendered pixels did not. `tools/collision.mjs` was written to settle it and
  showed no collision in any role. The claim was replaced with what was actually measured (F1). An earlier
  version of that tool counted ink *bands* and was discarded as unsound — a detached diacritic forms its own
  band, so a four-line block legitimately produces five.
- A first-pass bidi test reported that one of the seven hard cases changed order under isolation. That was an
  artefact of how the test tokenised the string, not a property of the layout; the per-character test
  corrected it to "no change in any case" (§9).

## 18. Reproduction

Node 24 and Chrome; no npm packages, no network access at build time.

```
node tools/font-facts.mjs   # font tables -> docs/MEASUREMENTS_font-tables.json
node tools/measure.mjs      # shaped-text measurement -> docs/MEASUREMENTS_rendered-text.json
node tools/collision.mjs    # rendered-pixel line collision -> docs/MEASUREMENTS_line-collision.json
node tools/build-all.mjs    # all 14 boards -> review/
node tools/check-render.mjs # greyscale / blank / palette fairness guard across review/
node tools/package.mjs      # the zip
```

`tools/system.json` is the single source of truth: the contract, the content and the controlled surface.
Every board and every measurement reads from it, which is what makes the content control real.
