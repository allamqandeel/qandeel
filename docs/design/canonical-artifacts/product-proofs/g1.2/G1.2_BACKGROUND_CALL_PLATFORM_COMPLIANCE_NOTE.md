# G1.2 — Background Call Platform / Store Compliance Note

**Task:** I-08B3.1-G1.2 — Voice + Live Conversation Experience Proof (background-safe / store-safe revision)
**Status:** bounded compliance note for review — **nothing here has been built in `apps/mobile`, and nothing here was verified on a device.**
**Sources:** read from the official Apple, Android, Google Play and Expo documentation on 2026-09-23 (§10). Where no primary
source was found, the note says so and marks the point **UNVERIFIED** instead of relying on a blog or a forum.

Every statement below carries one of four labels (brief §33):

| Label | Meaning |
|---|---|
| **PRODUCT REQUIREMENT** | locked by the Product Owner (brief §3–5) |
| **RECOMMENDED PRODUCTION ARCHITECTURE** | this note's recommendation for the future native implementation |

| **NOT YET IMPLEMENTED** | nothing in `apps/mobile` does this today; this proof adds nothing to it |

## 0. The answer in one paragraph

The locked behaviour is: a Live Call that the reader starts in the foreground keeps running, with the same call and the same
Conversation, when the screen locks or another app comes to the front. Coming back shows the last surface the reader left.
Both platforms support this when the call is a **genuine, user-visible, two-way voice call** and nothing else.

- **iOS:** one `AVAudioSession` in `playAndRecord` / `voiceChat`, kept active only for the call, plus the `audio`
  background mode. An outgoing CallKit call is **recommended** so the system treats it as a call. No PushKit, because
  there are no incoming calls.
- **Android:** `RECORD_AUDIO` is asked for at the moment of intent. The call is registered with Telecom through the
  Core-Telecom Jetpack library, which gives it foreground execution. It is started **while QANDEEL is visible**, and an
  ongoing-call notification (CallStyle, with Hang up) stays up as the platform's transparency, not as a defect. The Play
  Console foreground-service declaration must match exactly.
- **Expo:** the production call stack is **not** `expo-audio`. It is a native call-lifecycle module plus a real-time
  transport behind the Voice Adapter, integrated through Continuous Native Generation (config plugin / Expo Module). Any
  audio library the app adopts must have its default background declarations switched **off** unless a real feature
  uses them.

The machine-checked table of what production would declare — and the feature each item serves — is at the end (§11);
check **G12-11** rejects any item without a Live Call or Voice Note reason.

## 1. iOS

### 1.1 Microphone permission and purpose string — PRODUCT REQUIREMENT + RECOMMENDED

- **Purpose string (the key and the rule).** `NSMicrophoneUsageDescription` is required for any app that uses
  microphone APIs. Without it the app cannot record: AVAudioApplication's documentation says an app that tries to use the
  microphone without the key *exits*. App Review 5.1.1 requires purpose strings that "clearly and completely describe"
  the use.
- **Proposed string (PROOF copy, gender-neutral, T4 neutral register):**
  - Arabic: «يستخدم قنديل الميكروفون للرسائل الصوتية والمكالمات، وأثناء تشغيلها فقط.»
  - English: "Qandeel uses the microphone for voice messages and calls, and only while they are running."
- **When to ask.** Ask at the moment of intent: the first tap on the Voice Note or the Live Call control, **never at
  launch**. `AVAudioApplication.requestRecordPermission` prompts the first time only. After that it returns the stored
  answer, and a denied reader can grant access later only in Settings. Until permission is granted, input is silence.
- **Recording indication.** App Review 2.5.14 requires "a clear visual and/or audible indication when recording … any
  use of the device … microphone". Two things provide it: the in-app call line (the microphone state in words, the live
  level, the call time) and the system's own microphone indicator.
- **PROTOTYPE SIMULATION.** A labelled schematic of the OS prompt (`vn-01`, `pf-02`), shown only after the reader's
  act. The source check **G12-09** proves the browser microphone is requested only from that act.

### 1.2 Audio session for two-way voice — RECOMMENDED PRODUCTION ARCHITECTURE

- **Category `playAndRecord`.** Apple documents it as the category for "simultaneous recording (input) and playback
  (output) of audio … ideal for apps like VoIP applications".
  - It plays even when the Silent switch is on.
  - It is **nonmixable** by default: activating it interrupts other nonmixable audio. That is correct for a call.
- **Mode `voiceChat`.** "Your app is performing two-way voice communication, such as using Voice over Internet
  Protocol." It is appropriate with `playAndRecord`. It optimises equalisation for voice, reduces the allowed routes to
  those suitable for voice chat, and automatically applies `allowBluetoothHFP`.
- **Echo cancellation needs real voice processing.** Full voice processing (echo cancellation, automatic gain) applies
  only with Audio Unit Voice I/O or AVAudioEngine voice processing. "Using chat modes without these tools" reduces the
  processing. For an Analysis-first call played through the loudspeaker, echo cancellation is **not optional**, so the
  production audio path must use voice processing, not a plain player.
- **Route.** `playAndRecord` routes to the receiver unless told otherwise. An Analysis-first call is watched, not held to
  the ear, so the proof defaults the speaker ON (decision **G12-J4**). Production would express that with the session's
  speaker option or an output override. Other routes (Bluetooth, AirPlay) are the system route picker's.

### 1.3 Background continuation — PRODUCT REQUIREMENT → RECOMMENDED

- **The mode.** Apple: to keep playing audio "when transitioning to the background (e.g., when the screen locks), add
  the `audio` value to the `UIBackgroundModes` key". The `audio` mode is listed as "The app plays audible content in the
  background".
- **The call's lifetime.**
  - The session is activated when the call is established.
  - It stays active across lock and app switching.
  - It is **deactivated when the call ends**, after which iOS may suspend QANDEEL normally.
- **Use sparingly.** Apple's background-modes guidance: "Use background modes sparingly; overuse negatively impacts
  device performance and battery life."
- **NOT YET IMPLEMENTED.** `apps/mobile/app.json` declares no background mode. Check **G12-14** proves this proof
  changed no tracked file.

### 1.4 Store safety on iOS — hard constraint

- **Guideline 2.5.4:** "Multitasking apps may only use background services for their intended purposes: VoIP, audio
  playback, location, task completion, local notifications, etc."
- **What that means for QANDEEL:**
  - The `audio` background mode exists **only** because of the Live Call. It is used only while a call is active.
  - Never silent audio, and never a session left active to keep QANDEEL alive.
  - No background capture for a Voice Note (recommendation **R-VN**, final report §E).
  - The Analysis live driver keeps its T-12P law: foreground-only catch-up, **no background polling**. The Analysis
    catches up when QANDEEL returns. The call's audio is the only background work.
- **Rejected pattern.** A Skill on this host (`fishjam` › foreground-service) notes that enabling Picture-in-Picture
  support writes the `audio` background mode "as a side-effect". **Rejected:** a capability QANDEEL does not use must
  never be the route to a background mode. `audio` is declared directly, for the call.

### 1.5 System call integration — RECOMMENDED PRODUCTION ARCHITECTURE

- **CallKit, outgoing only.** QANDEEL calls start inside the app (brief §7), so:
  - The reader's tap requests a `CXStartCallAction` (with a UUID) through `CXCallController`.
  - The provider delegate *configures* the audio session. Apple's CallKit guide: "do not start call audio here. Call audio
    should not be started until the audio session is activated by the system, after having its priority elevated."
- **What CallKit gives.** The system's call UI and lock-screen presence, coordination with other calling apps, and
  respect for Do Not Disturb. The system manages audio-session activation.
- **Obligations that follow:**
  - Every system-initiated action ends or mutes **the same QANDEEL call**, and the app state converges: the system
    End, and a Bluetooth headset's End.
  - Mute from the system call UI must drive the same mute state the in-app control shows.
- **No PushKit (brief §7).** PushKit exists for *incoming* VoIP calls, and "for apps built using the iOS 13 SDK or later,
  PushKit requires you to use CallKit". G1.2 has no incoming QANDEEL call, so PushKit is **out of scope**. Adding incoming
  calls later is a separate, reviewed boundary: CallKit reporting of every VoIP push, a server push path, and consent.
- **The `voip` background mode (UNVERIFIED).** Apple lists it as "The app provides Voice over IP services". Whether an
  outgoing CallKit call needs it *in addition to* `audio` on the supported iOS versions is **not stated** in the
  documentation read. It is therefore **not declared** by default and is a native-spike question (§11,
  `conditionalNotDeclared`).
- **LiveCommunicationKit (iOS 17.4+).** Apple's newer framework "to initiate and handle VoIP … conversations". Its
  documentation does not compare it with CallKit. Evaluate it in the spike; it is not required.
- **Recents privacy (UNVERIFIED API detail).** A CallKit call may appear in the system's call history. For a private
  relationship that is a Product question (**G12-J8**). The provider configuration's recents option must be confirmed
  against the SDK in use.
- **Mainland China (UNVERIFIED).** No official Apple document was found. Only non-Apple community posts (Apple Developer
  Forums thread 772808, no Apple staff answer) report that CallKit is unavailable there. **Treat it as a risk to confirm
  with App Review** before distributing to that storefront. It does not change the design.

### 1.6 Interruptions — implementation + Product-visible

- **The notification.** `AVAudioSession.interruptionNotification` posts *began* / *ended*. Apple: check `shouldResume`,
  and do not assume playback resumes.
- **Another call.** An incoming phone call interrupts QANDEEL; with CallKit the system mediates hold and end.
- **Product-visible, and NOT DESIGNED in G1.2:** a call **held or interrupted by another call** is a new state. It is
  neither reconnecting nor ended, and it is recorded as open decision **G12-J6** rather than invented.

### 1.7 Route changes — implementation + one Product decision

- **The notification.** `routeChangeNotification` reasons include `newDeviceAvailable` (headphones connected) and
  `oldDeviceUnavailable` (headphones disconnected).
- **Apple's guidance is for playback apps.** When headphones are disconnected, "users … implicitly request privacy and
  expect playback to automatically pause".
- **For a live call:** the call must not end, but QANDEEL's voice must not suddenly go public on the loudspeaker. The
  proposal: fall back to the receiver and show the speaker toggle OFF. Product decision **G12-J4**.

## 2. Android

### 2.1 Runtime microphone permission — PRODUCT REQUIREMENT + RECOMMENDED

- **The permission and the workflow.** `RECORD_AUDIO` is requested with Android's documented runtime-permission flow:
  - **in context**, when the reader taps the Voice Note or Live Call control;
  - a rationale when `shouldShowRequestPermissionRationale` says so;
  - **graceful denial** ("Minimize functionality loss", "Don't block UI", "Accept user preference").
- **Repeated denial.** "If the user taps Deny for a specific permission more than once … the user will no longer see the
  system permissions dialog", which is permanent denial. QANDEEL then names the alternative and the Settings route. It
  never nags (proof `pf-01`, check **G12-P1**).
- **Microphone privacy.** Android 12+ shows a system microphone-access indicator that apps cannot hide. A user who turns
  microphone access off in Quick Settings gives the app **silent audio**. Production cannot tell that silence from a
  quiet reader by audio alone, which is a spike item (§9).

### 2.2 Foreground service — RECOMMENDED PRODUCTION ARCHITECTURE

- **`microphone` type** (`FOREGROUND_SERVICE_MICROPHONE`, needs `RECORD_AUDIO`).
  - It is for continuing microphone capture from the background (voice recorders, communication apps).
  - It is subject to **while-in-use restrictions**. Android 14+ states "an app in the background cannot create a
    microphone FGS, even if it falls into background start exemptions".
  - It **must be created while QANDEEL has a visible activity.** The reader's tap on the handset is exactly that moment.
- **`phoneCall` type** (`FOREGROUND_SERVICE_PHONE_CALL`, needs `MANAGE_OWN_CALLS` or the dialer role). It is for
  continuing ongoing calls using the `ConnectionService` / `android.telecom` APIs.
- **Android 14+ declarations.**
  - Every FGS declares its `foregroundServiceType` in the manifest.
  - The app holds `FOREGROUND_SERVICE` **and** the type's own `FOREGROUND_SERVICE_*` permission, or the system throws
    (`SecurityException` / `MissingForegroundServiceTypeException`).
  - `startForeground()` is called within a few seconds of the start.
  - A background start throws `ForegroundServiceStartNotAllowedException` (Android 12+).
- **The legal lifecycle (brief §8):**
  - The service and the call are established from the visible, user-initiated state.
  - The **same** call then continues as QANDEEL moves to the background.
  - Nothing ever starts the microphone later from an arbitrary background state.
  - A reconnection of the **same** call's transport while its service is running is part of that call. A call that has
    *ended* is never silently re-created from the background: the reader starts a new one (proof `bg-05`, `D3`).
- **Which types exactly.** `phoneCall`, plus `microphone` only if the Core-Telecom spike shows it is required alongside
  it. These are the **only** types. No `mediaPlayback`, no `dataSync`, nothing "just in case" (brief §9).

### 2.3 Telecom — RECOMMENDED PRODUCTION ARCHITECTURE

- **Core-Telecom rather than hand-built self-managed ConnectionService.** Android's self-managed guidance points to the
  `androidx.core:core-telecom` Jetpack library. It supplies:
  - registration: `CallsManager.registerAppWithTelecom`;
  - `addCall` with active / inactive / disconnect transitions;
  - audio endpoints: `currentCallEndpoint`, `availableEndpoints`, `requestEndpointChange`;
  - mute: `isMuted`;
  - remote surfaces: Bluetooth, wearables, Android Auto.
- **Foreground support, verbatim:** "The library uses `ConnectionService` (Android 13 API level 33 and lower) or
  foregroundtypes (Android 14 API level 34 and higher) for foreground support."
- **Notification timing:** "You are required to post a notification within 5 seconds of adding the call to the
  platform." Foreground priority is removed when the call ends or the notification is no longer valid.
- **Route APIs.** "Don't use the `AudioManager#setCommunicationDevice` or `AudioManager#startBluetoothSco` APIs to manage
  audio routes when using Telecom". The speaker toggle maps to `requestEndpointChange`.
- **Permission.** `MANAGE_OWN_CALLS`.
- **Minimum SDK.** The library's minimum SDK is confirmed at spike time against `apps/mobile`'s SDK line. It is not
  asserted here.

### 2.4 The persistent notification — PRODUCT REQUIREMENT (transparency), not a defect

- **What it is.** An ongoing-call **CallStyle** notification (`NotificationCompat.CallStyle.forOngoingCall`, with a
  Hang-up `PendingIntent`), belonging to the call's foreground execution.
- **Why it works for a call:**
  - It is ranked at the top of the shade on Android 12+.
  - It is exempt from Android 14's change that made other ongoing foreground notifications dismissible (CallStyle,
    media and DPC notifications are excepted).
- **Product stance (brief §8, Q8).** QANDEEL does not hide it, restyle it into a disguise, or treat it as a defect. It is
  the platform telling the reader, truthfully, that a call is running.
- **`POST_NOTIFICATIONS` (Android 13+)** is requested with the call's first run. How the ongoing-call notification
  behaves when that permission is denied was **not confirmed** from an official page read here (the page URL returned
  404). **UNVERIFIED: spike item.**

### 2.5 The user can always stop it — PRODUCT REQUIREMENT

- **In the app:** End call.
- **From the notification:** Hang up.
- **From Bluetooth / Android Auto:** through Core-Telecom's remote actions.
- **From the Task Manager (Android 13+).** Tapping Stop "stops the entire app … No callback is sent to the app".
  QANDEEL treats that exactly like a process end:
  - on the next launch it may read `ApplicationExitInfo` (`REASON_USER_REQUESTED`);
  - it must not show the call as live (proof `bg-06`).

### 2.6 Audio focus

- **Communication usage and focus.** Use `AudioAttributes.USAGE_VOICE_COMMUNICATION` and request `AUDIOFOCUS_GAIN`,
  because a call is sustained two-way audio. With Core-Telecom, focus and routing cooperate with the platform.
- **Focus loss.** Android's guidance for permanent loss is to pause and require explicit user action. For QANDEEL that is
  the same **held / interrupted** state as iOS §1.6: open decision **G12-J6**.

## 3. Google Play

**Declaration.** For apps targeting Android 14+, every foreground-service type used is declared in **Play Console →
App content**. For each type, Play asks for:

1. a description of the app functionality using it;
2. the user impact if the system defers or interrupts the task;
3. **a link to a video** showing how the user triggers the feature;
4. the matching use case from Play's list. `TYPE_PHONE_CALL` → "Calling: Cellular/VoIP/Telecom APIs";
   `TYPE_MICROPHONE` → capture audio input (voice commands, voice recording).

**Policy (Device and Network Abuse → foreground services).** A foreground service is permitted only for a feature that
is:

- "beneficial to the user and relevant to the core functionality";
- "initiated by the user or is user perceptible";
- "can be terminated or stopped by the user";
- cannot be deferred without degrading the experience;
- run "only for as long as necessary".

The Live Call meets each condition *by design*: the reader starts it, the reader hears it and the notification shows it,
End / Hang up / Task Manager stop it, a call cannot be deferred, and it ends with the call.

**What QANDEEL must never do:**

- Declare an unused type. `expo-audio`'s `enableBackgroundPlayback` defaults to **true** and adds a `mediaPlayback`
  foreground service and `FOREGROUND_SERVICE_MEDIA_PLAYBACK` on Android, so it must be set to **false** (§4). Otherwise
  Play would ask QANDEEL to justify a service it does not use.
- Request an unrelated high-risk permission. `android.blockedPermissions` strips anything a library merges in.

**The demonstration video.** The G1.2 motion recordings (C: background → restore; D2: failure) are storyboards for it. The
submitted video must show the **production** app, not this prototype.

**Watch item.** Play published an April 2026 policy preview. Its FGS change removes geofencing as a use case (effective
2027-01-27) and does not touch microphone or phone-call use.

## 4. Expo

- **Today.** SDK 57, React Native 0.86.3, New Architecture only, Continuous Native Generation (`ios/` and `android/` are
  generated and never committed). `apps/mobile/package.json` contains no audio or call library, and `app.json` declares
  no permission or background mode. **NOT YET IMPLEMENTED:** all of it.
- **What `expo-audio` (SDK 57 docs) gives:**
  - config-plugin options `microphonePermission`, `recordAudioAndroid`, `enableBackgroundRecording` (default false) and
    `enableBackgroundPlayback` (**default true**, which adds iOS `audio` and an Android `mediaPlayback` service);
  - `setAudioModeAsync` with `allowsRecording`, `playsInSilentMode`, `shouldPlayInBackground`,
    `allowsBackgroundRecording`, `interruptionMode` and `shouldRouteThroughEarpiece`;
  - `requestRecordingPermissionsAsync`;
  - real-time PCM capture (`useAudioStream`);
  - on Android, background recording as a foreground service that shows a persistent notification reading "Recording
    audio", with a stop button.
- **Why `expo-audio` is not the Live Call stack (brief §10):**
  1. It documents **no real-time PCM output** for two-way voice.
  2. It documents no CallKit, no Telecom and no voice-processing (echo-cancelling) path.
  3. Its Android background-recording notification says "Recording audio". For a live call that may simply be
     **false** (VI-01 §14: "Recording" may be false if the call is not persistently recorded), and it is not a call
     notification.
  4. Its background-playback default would declare a service QANDEEL does not use.
- **Where `expo-audio` could fit:** at most the **foreground** Voice Note (capture, playback), with both background
  options explicitly **off**.
- **RECOMMENDED PRODUCTION ARCHITECTURE (the cleanest supported path).**
  - **(a) A native call-lifecycle layer:** CallKit on iOS, Core-Telecom on Android. Either a maintained library whose
    background and permission declarations can be controlled, or an Expo Module QANDEEL owns.
  - **(b) A real-time two-way audio transport with platform voice processing, behind the Voice Adapter** (Foundation
    Freeze: provider independence). Candidates are the Tech Stack's GPT Realtime / Gemini Live / cascaded
    STT → Runtime → Speech Rendering → TTS, benchmark-driven. A WebRTC-class media path supplies echo cancellation.
  - **(c) Integration through CNG**, following `apps/mobile/README.md`'s hierarchy: config plugin pre-authorized; Expo
    Module pre-authorized with the frozen requirement named; direct edits of generated native projects **not**
    pre-authorized. Background modes, permissions and services are declared in `app.config` / plugins, and
    `android.blockedPermissions` removes whatever a dependency merges but QANDEEL does not use.
- **Candidates seen on this host (Skill evidence only, not platform documentation, not chosen).**
  - A WebRTC SDK whose React Native client exposes CallKit, foreground-service and audio-output hooks (`fishjam`).
  - `react-native-audio-api` for a native audio graph. It too ships background-recording plugin options that must be
    set deliberately.
  - Choosing one is the Voice / Live Call track's decision; G1.2 implements no provider.

## 6. Background / foreground legality — the call's legal timeline

| Step | iOS | Android | Legal because |
|---|---|---|---|
| 1. Reader taps the handset in QANDEEL | visible app | visible activity | user-initiated, perceptible |
| 2. Microphone permission (first time) | system prompt | system dialog | asked in context |
| 3. Call registered with the system | `CXStartCallAction` | `CallsManager.addCall` | a real call |
| 4. Foreground execution established | session configured; activated by the system | FGS started **while visible**, notification within 5 s | while-in-use rule satisfied |
| 5. Two-way audio | `playAndRecord` / `voiceChat` with voice processing | `USAGE_VOICE_COMMUNICATION`, `AUDIOFOCUS_GAIN` | the feature itself |
| 6. Screen locks / another app | `audio` mode keeps the session | FGS + Telecom keep the call | the SAME call continues |
| 7. Reader returns | UI re-renders from the in-process call controller | same | no restart, no second session |
| 8. Call ends (any path) | session deactivated; CallKit ended | call disconnected; FGS stopped; notification removed | runs "only as long as necessary" |

**Never:**

- starting the microphone from the background;
- re-creating an ended call from the background;
- keeping any session, service or notification after the call has ended;
- background polling for the Analysis.

## 7. User-visible stop / end requirements

Every path ends **the same call**, and QANDEEL's state converges on it.

**The end paths:**

- End call in QANDEEL (the Conversation or the Analysis);
- the system call UI's End (CallKit);
- Android's ongoing-call notification Hang up;
- a Bluetooth / car control (Telecom remote actions, CallKit);
- Android Task Manager Stop (process end);
- iOS force-quit (process end).

**Two results:**

- **An end the reader chose in QANDEEL:** the reader stays where they are (G1.1 behaviour), and the history records
  «مكالمة صوتية · m:ss».
- **Any end the reader did not choose in QANDEEL** (network failure, a system end while away): QANDEEL returns to the
  Conversation, V07 «المكالمة وقفت. الكتابة متاحة.» names the event and the alternative, Writing is reachable, and no
  call control is shown (checks **G12-Q10**, **G12-M2**).

A process end leaves nothing live. The cold start restores the T-13 durable viewpoint and shows no call (proof `bg-06`).

## 9. Production risks

| R1 | A library silently declares background modes / FGS types QANDEEL does not use (e.g. `expo-audio` background playback defaults to true) | declare every capability explicitly in `app.config`, set library defaults off, `android.blockedPermissions`, and a CI check that diffs the generated manifest / Info.plist against §11 |
